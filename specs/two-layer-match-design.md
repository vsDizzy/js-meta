# Двухслойный match: проект этапа 2

Дата: 2026-11-20. Основание: `specs/two-layer-match-research.md` и решения из его раздела 5. Проект принят и реализован 2026-11-20. Отступления от него записаны в `specs/decisions.md` (запись «Two-layer match: as built»), найденные неудобства — в `specs/todo.md`.

## Главная идея

**Паттерн — обычное дерево, в котором могут стоять узлы семейства `pat/`.** Так устроено и сейчас: паттерн — дерево кода, где особый узел — идентификатор `$a`. Ядро обобщает «особый узел» до набора видов `pat/bind`, `pat/rest`, `pat/or` и так далее. Отсюда три следствия:

- Обычный узел внутри паттерна — литерал: совпадает **точно**, как сегодня.
- `pat/node` — проверка вида с именованными полями: совпадает **частично**, неупомянутые поля игнорируются. Это и есть решение «частично внизу, точно в `js`»: режим задаёт вид узла паттерна, а не флаг.
- Паттерны остаются данными в той же форме `{ type, ...attrs, children }`: их можно обходить `walk`, печатать, собирать шаблонами. Смешанное дерево не требует ничего особого.

Сахар `js` переводит `$a`, `$$a`, обёртки и комментарии-переменные в узлы `pat/` один раз на паттерн (кэш по узлу-корню; `js` без дырок возвращает один и тот же объект на место вызова).

## 1. Семейства

Семейство определяется префиксом вида: `lua/CallExpression` → `lua`, `clj/list` → `clj`, без префикса → ESTree. `Comment` — общий вид для всех семейств: `walk` и `match` уже знают его.

```ts
defineFamily('clj', {
  // всё необязательно; значения по умолчанию в скобках
  ignored?: string[]                       // атрибуты, не влияющие на смысл ([])
  equal?: { [kind]: (a, b) => boolean }    // особое сравнение атомов (все атрибуты по значению)
  canon?: (kind) => string                 // эквивалентные виды (тождество)
  unwrap?: (node) => Node | undefined      // «оператор-обёртка выражения» (нет)
  isStatement?: (kind) => boolean          // (false)
  head?: (node) => string | undefined      // голова для индекса (нет)
  resolve?: (node, ctx) => string | undefined  // голова через связывание (нет)
  position?: (parentKind, slot) => 'statement' | 'expression' | undefined
  tail?: (parentKind, slot) => 'return' | 'pass' | undefined   // см. раздел 4
})
```

Семейство ESTree собирается из того, что сейчас зашито в `match.ts`:

| Поле | Содержимое |
|---|---|
| `ignored` | `raw`, `shorthand`, `expression`, `comments` |
| `equal` | `Literal` (значение, regex, bigint), `TemplateElement` (`cooked`), `JSXText` |
| `canon` | декларация и выражение функции; то же для класса |
| `unwrap` | `ExpressionStatement` без `directive` |
| `head` | имя вызываемого у `CallExpression`, `NewExpression`, `TaggedTemplateExpression`; имя тега у `JSXElement` |
| `resolve` | `scope.bindingOf(callee)?.import` → `source#name` |

Две странности из исследования исправляются здесь же: `value` и `declare` уходят из общего списка игнорируемых. `value` остаётся только в трёх особых сравнениях, поэтому у чужого атома он значим. `declare: false` и так считается отсутствием атрибута.

Семейства `clj` и `lua` в этапе 2 — это только `define` видов с префиксом, `head` и `unwrap` (`lua/CallStatement`). Ридеров нет, тесты собирают узлы руками.

## 2. Виды паттернов

Строители живут в `p`. Все возвращают `Node`.

| Строитель | Вид | Смысл |
|---|---|---|
| обычный узел | — | литерал: тот же вид (с учётом `canon`), равные значимые атрибуты, слоты совпадают точно |
| `p.bind('a', of?)` | `pat/bind` | захват; с `of` — захват при совпадении вложенного паттерна |
| `p.any()` | `pat/any` | что угодно, без захвата |
| `p.node(kind, fields?)` | `pat/node` | проверка вида; `kind` — строка, массив или группа (`Function`). `fields`: имя слота → паттерн, имя атрибута → значение или паттерн. Неупомянутое игнорируется |
| `p.rest('a', of?)` | `pat/rep` | отрезок списка, как `$$a` |
| `p.rep(of, { min, max, name? })` | `pat/rep` | повторение; `p.opt(of)` — это `{ min: 0, max: 1 }` |
| `p.group(...items)` | `pat/group` | несколько подряд идущих элементов как одно целое: пары в `let` — `p.rep(p.group(p.bind('n'), p.bind('v')))` |
| `p.or(...alts)` | `pat/or` | альтернатива |
| `p.not(of)` | `pat/not` | отрицание; ничего не захватывает |
| `p.guard(of, (caps, node, ctx) => boolean)` | `pat/guard` | условие с доступом к захватам и ctx |
| `p.comment('c', { seq?, doc? })` | `pat/comment` | переменная-комментарий; стоит там же, где стоял бы комментарий |

Правила, которые стоит зафиксировать:

- **Захваты внутри `rep`** становятся массивами, по элементу на повторение.
- **Повтор имени** требует равного кода, как сейчас. Сравнение — тем же матчером без переменных, значит символы cljs сравниваются по `ns` и `name`, а не по ссылке.
- **Захват атрибута:** `p.node('BinaryExpression', { operator: p.bind('op') })` кладёт в захваты строку.
- **`or` — упорядоченный выбор.** Берётся первая подошедшая альтернатива; если дальше по дереву совпадение сорвётся, к следующей альтернативе матчер не возвращается. Возвраты есть только внутри одного списка, как сейчас. Причина: полный перебор усложняет матчер, а в правилах пяти языков не понадобился ни разу.
- **Комментарии** работают как после `91f239f`: комментарий в паттерне (в `comments` литерала или соседом в списке) — требование. `p.not` закрывает случай «комментария здесь нет».
- **«Выражение матчит оператор»** остаётся: если цель — обёртка (`unwrap`), а паттерн — литерал не-оператор или `pat/node` с не-операторным видом, сравнивается содержимое обёртки.
- **Раскрытие ребёнка в паттерне** (`,[e]` из nanopass) откладывается. Вместо него `ctx.expand` в guard и в функции-замене (раздел 4).

## 3. Шаблоны результата

```ts
build(template, captures): Node | Node[]
```

Шаблон — дерево с `pat/bind` и `pat/rep`: первый заменяется захватом, второй вклеивается в список. Никаких приведений типов ядро не делает. Захваченные узлы вставляются как есть, поэтому их позиции в исходнике сохраняются; корень замены получает позицию и комментарии заменяемого узла в `walk`, как сейчас.

`substitute` и `fill` в `src/quote/index.ts` не трогаются. Это сахар JS для шаблонов (роли дырок, превращение выражения в оператор), он уже работает и на чужих узлах. Перевод его на `build` — отдельная работа, в критерии приёмки она не входит.

## 4. Правила, индекс и ctx

### Индекс

`rule(pattern, replace, options?)` и `rules(...)` сохраняют сигнатуры. У правила появляется ключ, вычисленный из корня паттерна: набор видов (или «любой») и голова (или «любая»). `rules` строит таблицу вид → голова → правила. На узле берутся корзины для его вида, для вида его содержимого (если он обёртка) и корзина «любой вид»; кандидаты сливаются по порядковому номеру, чтобы «побеждает первое» сохранилось. Произвольная функция с `.once`, но без ключа, попадает в «любой вид».

Голова по связыванию включается явно:

```ts
rule(js`assert($c)`, …, { from: { source: './macros.js', name: 'assert' } })
```

Такое правило срабатывает, только если голова разрешается в этот импорт, под любым локальным именем, и не срабатывает на затенённом имени. Без `from` поведение прежнее, по имени.

### ctx

`Ctx` из `walk` расширяется ленивыми полями; старые поля не меняются.

| Поле | Смысл |
|---|---|
| `ctx.scope` | `ScopeInfo` корня обхода, считается при первом обращении |
| `ctx.position` | `'statement'`, `'expression'` или `null`, из таблицы семейства родителя |
| `ctx.tail` | узел в хвостовой позиции: слот `return` либо слот `pass` у родителя, который сам в хвосте |
| `ctx.env` | неизменяемый объект пользователя, наследуется детьми |
| `ctx.expand(node, env?)` | раскрывает поддерево тем же визитором так, как если бы оно стояло здесь; результат помечается готовым, `walk` в него повторно не заходит |
| `ctx.send(tag, value)` | сообщение вверх |
| `ctx.receive(tag, fn)` | выполняет `fn` и возвращает `[результат, сообщения]`, перехватив всё, что отправлено с этим тегом изнутри |

Пример канала вверх, Lua: цикл раскрывает тело и узнаёт, был ли в нём `goto continue`.

```ts
const [body, gotos] = ctx.receive('goto', () => ctx.expand(m.body))
```

Известное ограничение: `ctx.scope` — снимок исходного дерева. Узел, созданный шаблоном, в нём не найден, и его голова разрешается по имени на уровне модуля. Захваченные узлы сохраняют идентичность, для них разрешение точное.

## 5. Верхний слой (этап 3 задания)

`match(node, pattern, ctx?)` остаётся: переводит паттерн в узлы `pat/` и зовёт ядро. Перевод:

- `$a`, `$_`, `$$a` и четыре нынешние обёртки → `pat/bind`, `pat/any`, `pat/rep`;
- комментарии-переменные → `pat/comment`;
- всё остальное остаётся литералом.

Новое в сахаре (третья странность и соседние пробелы из исследования):

- `$x: $T` — аннотация на переменной перестаёт теряться: `x` захватывает параметр целиком, `T` — тип. `$x` без аннотации по-прежнему матчит параметр с любой аннотацией или без неё.
- `$T` в позиции типа (`TSTypeReference` из одного имени без аргументов) — переменная для любого типа. После этого `$x as $T` матчит `foo as string`.

Старый класс `Matcher` удаляется, когда все тесты `quote.test.ts` проходят через ядро без правок.

## 6. Порядок работ

Каждый шаг — отдельное задание субагенту; после каждого — `pnpm test` и `pnpm exec tsc`.

1. **Семейства.** `defineFamily`, префиксы видов, ESTree-семейство; нынешний `Matcher` переведён на него; тесты на `value` и `declare`.
2. **Ядро.** `src/match/`: виды `pat/`, строители `p`, матчер, `build`. Тесты на низком уровне для `clj`, `lua` и смешанного дерева; сравнение символов по значению.
3. **Сахар.** `match` через ядро, старый `Matcher` удалён, все прежние тесты проходят без правок. Аннотация на переменной и `$T` в позиции типа.
4. **Индекс** в `rules`, опция `from`.
5. **ctx:** `scope`, `position`, `tail`, `env`, `expand`, `send` / `receive`.
6. **Приёмка.** По одному нетривиальному правилу на язык: `when` (cljs), `and` с рекурсией (Lisp), опциональная цепочка (JS), стирание аннотаций (TS), `local function` (Lua). Тест на смешанное дерево. Скрипт замера с таблицей «до и после».

## Что не входит

Ридеры и печать для cljs, Lisp и Lua; перевод `substitute` на `build`; раскрытие ребёнка внутри паттерна; обёртки для `interface { $$m }`, `enum`, `import { $$s }`, `<$T $$attrs />`; гигиена имён в шаблонах.
